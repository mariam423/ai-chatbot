# Pulse AI — Production Scalability Refactor Plan

> Status: **Phases 0–6 nearly complete and green** (`npm run check` passes: typecheck ✓, 546 tests). Phase 6's fault-injection tests and docs sweep are done; only the optional load smoke remains. Each phase lists its done-criteria so a reviewer can confirm closure.
>
> Scope: take the single-instance Next.js 16 chatbot ("Pulse AI") to a hyper-scalable backend — background worker queues, tuned Postgres pooling, distributed caching + tiered rate limiting, and a resilient multi-provider LLM gateway — **without breaking** streaming chat, auth, schema, or Vercel production stability.

### Phase 1 — Async worker queues (DONE)

- Dedicated BullMQ connection (`maxRetriesPerRequest: null`) used by queue **and** worker — the shared serverless-tuned client is never reused for blocking commands.
- `document:process` performs real ingestion offload: large uploads (> 50 chunks) return immediately after creating the Document row; the worker chunks, embeds, and bulk-inserts chunk rows (`storeDocumentChunks`), then invalidates session/user caches. `addTask` returning `null` (Redis down) → the route ingests synchronously — the upload contract never regresses.
- `document:embed` implemented (idempotent upserts, deterministic embeddings); `webhook:stripe:post-process` queue + inline cache-invalidation fallback wired into the Stripe route.
- Worker now boots: `tsx` devDependency resolves `@/` aliases + TS; `npm run worker`, `scripts/worker.mjs`, PM2 interpreter fixed.
- **Done-criteria met:** worker suite + queue-connection assertions green; `tsx` boots the worker module with all 5 handlers; upload/webhook/rag tests green.
- **Known leftovers (next phases):** `analytics:aggregate` stub, `cache:invalidate` pattern handler, upload "processing" UI state, queue observability endpoint.

### Phase 2 — Database pooling & connection strategy (DONE)

- New pure module `lib/db-config.ts`: `DATABASE_POOL_MAX`/`MIN`/`IDLE_TIMEOUT_MS`/`CONNECTION_TIMEOUT_MS` envs with runtime-aware defaults — no env on a long-lived process resolves to exactly node-postgres defaults (zero behavior change); on Vercel the per-instance `max` defaults to 1. Invalid env values fall back rather than crash; `min` is clamped to `max`. `buildPrismaPgConfig` feeds `new PrismaPg(...)` in `lib/db.ts`.
- Startup warning when a serverless runtime points at a Neon _direct_ URL (no `?pgbouncer=true`) — the pooled URL is what keeps function bursts under Neon's connection limit.
- SSL is URL-driven (`?sslmode=require`, `verify-full` for stricter) — verified pg parses it via `pg-connection-string`; documented, no adapter code needed.
- Index audit: existing Postgres indexes (see ground-truth table) already cover the sidebar list's per-session aggregations; no new index added (an extra write-side index on the highest-write table wasn't justified for per-user sorts of dozens of rows).
- Tests: `tests/db-config.test.ts` (13 cases) — defaults, serverless cap, env overrides, invalid-input fallback, min clamp, warning matrix.
- Docs: `.env.example` + `docs/environment-variables.md` (Database pooling section).
- **Done-criteria met:** check green (502 tests at the time); docs updated; no schema change; no behavior change without env overrides (non-serverless defaults == pg defaults).

### Phase 3 — Distributed cache & rate-limit completion (DONE)

- **Sidebar list caching**: `lib/cache.ts` gained per-user sidebar page helpers (`getCachedSessionList`/`setCachedSessionList`/`invalidateCachedSessionList`, key `sessions:list:<userId>:<archived>:<skip>:<take>`, 30 s TTL). `listChatSessions` serves the default (search-less) list from cache and repopulates on miss — signed-in users only (an anonymous key would be shared across browsers) and never for search results. Invalidation fires after every session mutation that could reorder or change the list: save, rename, delete, pin, archive, skill override, active-branch, system prompt. Per-session keys were deliberately not used for the sidebar — they can't serve a paged multi-row list; the existing `session:meta:*` helpers stay for the worker's per-session invalidation.
- **Billing status cache**: `getBillingStatus` (settings + dashboard) now reads `getCachedBillingStatus` first (30 s TTL) and populates on miss. `CachedBillingStatus` gained `estimatedTokensToday`; values written before the field existed are treated as a miss. `checkAndRecordUsage` invalidates the cache after every recorded request (fire-and-forget) so displayed usage stays fresh — enforcement never routes through this cache.
- **Tier limiter**: `FREE_PLAN_BURST_PER_MINUTE` env knob (default 20, mirroring `FREE_PLAN_DAILY_LIMIT`; Pro stays 120/min); the `/api/chat` tier denial now returns the guardRoute 429 shape — JSON `{ error }` plus a `Retry-After` header when the limiter knows the reset time (burst denials). `invalidateAllUserCache` now clears the session-list pages too.
- **Done-criteria met**: integration tests with a fake Redis in `tests/actions.test.ts` (list page served after the DB is wiped + invalidated by rename; search bypasses cache; billing cached until invalidated; usage record drops the cache), `tests/cache.test.ts` page round-trip/key isolation/pattern purge, tier env-knob test, and an `/api/chat` 429-shape route test. Full `npm run check` green (514 tests).

### Phase 4 — Resilient multi-provider LLM gateway (DONE)

**Goal:** if the primary provider/model is sick (429/5xx/408, pre-stream connect failure, dead slug), traffic fails over to the next-ranked provider **without interrupting an active stream**.

Delivered in `lib/gateway.ts` + `app/api/chat/route.ts`:

- **Candidate ranking** (`listGatewayCandidates`): a per-user key from Settings (detected by prefix — OpenRouter/Gemini/OpenAI) is always first, then the server env keys in canonical rank OpenRouter → Gemini → OpenAI, each carrying its own key + base URL (all OpenAI-compatible `/chat/completions`). Duplicate providers collapse to the user key. No key at all → the existing 500 "not configured".
- **Circuit breaker** (per provider, closed/open/half-open): failures within a 60 s window (3 by default — `GATEWAY_FAILURE_THRESHOLD`) open the breaker for a 30 s cooldown; state lives in Redis (`pulse:gateway:breaker:<provider>`, TTL = window + cooldown so stale keys self-expire) with a per-process in-memory fallback when Redis is down — a Redis outage cannot widen an LLM outage. A request to an open provider is skipped for the next-ranked provider; when every breaker is open (or only one provider is configured) nothing is skipped — the request itself is the half-open probe, and its success closes / its failure reopens the breaker.
- **Attempt chain**: every usable provider first tries its own `resolveModel`-mapped selected model (namespaced OpenRouter slug vs plain Gemini name — resolveModel was already provider-aware), then the provider's stable backup id when the two differ — the historical single-provider retry, preserved exactly, with the no-loop guard. A hop keeps the same shape and serves the next provider's model id + backup.
- **Widened pre-stream trigger set**: 404/402/408/429, every 5xx, and thrown connect errors (DNS/TLS/refused) now retry/hop instead of surfacing. A chain that dies purely on connect failures returns the canned 502; an exhausted chain with retryable statuses passes through the last status + first 500 chars of `detail` (the historical passthrough contract). Non-retryable 4xx (400/401/403…) still surface immediately — a malformed request or bad key is not provider sickness.
- **Stream-preserving**: the loop stops the moment a streaming response head arrives and the body passes straight through — mid-stream errors surface to the client as partial content (the streaming contract, unchanged). The 90 s wall clock stays a _global_ budget (Vercel function-seconds): a hop after it fires is not attempted — the request returns the 504 timeout as before.
- **Headers**: `X-Served-Model` / `X-Served-Model-Overridden` (unchanged semantics — overridden now also true when a request starts in failover because the primary was circuit-open) plus new `X-Served-Provider` so a caption can say "fell back to Gemini". The client-side caption rendering of the new header is a tracked follow-up (it would need the provider stored per message through thread persistence + export).
- **Telemetry**: `gateway_failover` (info) on every cross-provider hop and `gateway_exhausted` (info) when the whole chain fails — structured `lib/audit.ts` events, ids/statuses only, gated behind `SECURITY_AUDIT_LOG` like other info events. `resetGatewayBreakers()` exported as a test/ops escape hatch.
- **Done-criteria met**: `tests/gateway.test.ts` (14 tests — candidate ranking, memory + Redis-backed breaker state, half-open reopen/close, per-provider isolation, window slide); `/api/chat` contract tests for primary 503 → secondary streams, connect-error hop, primary open-circuit → secondary without a first attempt, widened 408 retry, non-retryable 4xx surface, all-providers-fail passthrough, and single-provider probe-when-open (7 tests). Mid-stream partial-content behavior and single-provider 404/402/429 retries unchanged (existing `tests/api-chat.test.ts` + `tests/api-embed.test.ts` all green); full `npm run check` green (546 tests). Live "primary key exhausted → falls to secondary" check is a manual/CI-optional step like `tests/live-providers.test.ts`.
- **Effort:** 3–5 days → landed (one focused session + the surrounding suite hardening).

### Phase 5 — Observability & operations (DONE)

- **Admin-gated queue metrics**: new `GET /api/health/queue` (`app/api/health/queue/route.ts`) behind a new `ROUTE_GUARDS['health-queue']` entry (session required, CSRF off for a read-only GET, 120/min IP cap) with the ADMIN role enforced in the route via `normalizeUserRole` on the session user (mirrors `getDashboardData`; bypassed under `AUTH_DISABLED`). `/api/health` stays a public DB-only liveness probe. Returns BullMQ depths from `getQueueMetrics()` — which already existed in `lib/queues/task-queue.ts` and returns `null` without Redis — as `queue: null` on a clean 200 when Redis isn't configured.
- **Worker env knobs**: `WORKER_CONCURRENCY` (default 5) and `WORKER_LIMITER_MAX` (default 30/s) replace the hardcoded values in `startWorker`, parsed with the same safe fallback as `lib/db-config.ts` (garbage env → defaults). The completed handler logs job durations (from BullMQ timestamps) and the failed handler emits a structured `worker_job_failed` audit event with the attempt count (ids only — never the error message, which can carry document text). Added `attemptsMade` to the vendored `types/bullmq.d.ts` Job type.
- **Worker env-loading bug fixed**: `scripts/worker.mjs` never loaded `.env.local`, so on EC2 the PM2 worker would boot without `DATABASE_URL`/`REDIS_URL` (Next loads the file itself; a plain Node process doesn't). It now loads `.env.local` then `.env` (quiet, real process env wins — PM2 `NODE_ENV=production` can't be clobbered). `dotenv` added as a direct dependency.
- **Ops docs**: `AWS_EC2_DEPLOYMENT.md` documents the Redis requirement + graceful degradation without it (worker exits, synchronous upload fallback, no-op cache, in-memory rate limits), PM2 restart policy, worker env knobs, and the `/api/health/queue` admin endpoint; the stale LibSQL paragraph and the broken `ecosystem.config.js` duplicate (worker pointed at plain `node`, not tsx) were removed — `.cjs` is the single config.
- **Done-criteria met**: `/api/health/queue` route contract tests (200 + metrics shape, 200 + `queue: null` without Redis, 401 no session, 403 non-admin/ghost user, AUTH_DISABLED bypass) in `tests/health-queue.test.ts`; worker env-knob + job-event tests in `tests/task-worker.test.ts`; `ROUTE_GUARDS` pinning extended in `tests/security.test.ts`. Full `npm run check` green (525 tests).

## Risks & mitigations

| Risk                                                                  | Sev  | Mitigation                                                                                                                                                                                                                                                  |
| --------------------------------------------------------------------- | ---- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Redis outage widens into an app outage                                | High | Every Redis consumer degrades (memory limiter, no-op cache, synchronous job fallback); breakers degrade to per-process state; failure paths are tested                                                                                                      |
| Shared Redis client reused for BullMQ blocking commands corrupts jobs | High | **Fixed** — dedicated `maxRetriesPerRequest: null` connection; asserted in tests                                                                                                                                                                            |
| Offloaded document processing regresses upload UX                     | Med  | Hybrid: small docs stay synchronous (unchanged path); large docs return immediately with a usable Document row; retrieval skips not-yet-ingested docs gracefully; Redis-down fallback keeps the contract                                                    |
| Worker process can't boot in prod (alias/TS resolution)               | High | **Fixed** — tsx interpreter in PM2 + `npm run worker`; verified import boots all handlers                                                                                                                                                                   |
| Postgres migration history broken (SQLite DDL on a pg provider)       | High | **Fixed** — squashed to one Postgres init migration; CI e2e now runs against a real Postgres service                                                                                                                                                        |
| Pool exhaustion during serverless spikes                              | Med  | Phase 2: per-runtime pool caps + Neon pooled URL enforcement + connection timeouts                                                                                                                                                                          |
| Stale billing/sidebar data in the settings/list hot paths             | Low  | **Addressed** — Phase 3: short TTLs (30 s) bound staleness; every mutation/webhook/usage-record invalidates; cache is an optimizer, never a source of truth                                                                                                 |
| Cross-provider failover breaks the streaming contract                 | Med  | **Addressed** — Phase 4: failover is strictly pre-stream (the attempt loop stops at the first streaming head; mid-stream errors surface as partial content); pinned by the route contract tests + `e2e/proxy-stream.spec.ts` / `e2e/fallback-retry.spec.ts` |
| Circuit breaker causes cross-provider data-format surprises           | Low  | All providers are OpenAI-compatible endpoints (already the design); model resolution is provider-aware                                                                                                                                                      |
| Stale cache after plan change / rename                                | Low  | **Addressed** — webhook + worker + every session mutation invalidate (inline fallback when Redis is down); TTLs bound any residual staleness                                                                                                                |
